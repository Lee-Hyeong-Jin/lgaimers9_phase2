### 1.2 문제 설명·평가 탭·데이터 설명서
- 평가 산식 `100000 × (1 − Brier / r(1−r))`, **Public = 테스트 100%, Private = 종료 시점의 Public**, 최고점 제출물이 최종(FAQ 08-14 #16, 08-19 #24-2).
- 실행 환경: Python 3.11.15, 6 vCPU, 28 GB RAM, L4 22.4 GB, CUDA 12.8, 기본 설치 `torch==2.7.1+cu128, pandas==2.0.3, numpy==1.26.4, scipy==1.15.3, scikit-learn==1.8.0, joblib==1.5.3, transformers==4.46.3`; 설치 ≤10분, 추론 ≤10분, 용량 ≤10 GB(압축 해제 32 GB), 인터넷 불가.
- 데이터 설명서 5) 금지 예시: test 내부 행을 이용한 선수/팀/월별 누적 통계, 빈도·분포 통계, target encoding, 행 순서 기반 rolling/expanding, 평가 데이터 전체를 보고 만든 사후 보정값. `asof_*`는 공식 입력이므로 사용 가능.
- 데이터 설명서 6) 사용 금지 정보: 현재 투구 이후 확정 정보, 현재 투구의 위치·판정·결과·구종·Trackman 측정값, 2025 Trackman, 평가 데이터 내 다른 행으로 만든 누적/빈도/분포/rolling/target encoding.

### 1.3 재안내 (talkboard/417123, 2026-08-13, DACON.GM)
- 행 A의 예측값은 **① A의 입력 변수 ② A의 입력만으로 만든 파생변수 ③ 공식 학습 데이터 ④ 공식 학습 데이터만으로 만든 통계·모델·파생변수**만으로 생성.
- 허용되지 않음: test 내 다른 행의 누적 통계·rolling/lag, test 전체의 평균·분포·빈도·순위를 이용한 보정, 같은 선수·팀·월·경기 단위의 test 내 집계, 시점상 과거로 보이는 test 행 이용.
- 판정 예시: **"test.csv에 해당 행 1개만 있는 경우"와 "전체가 함께 있는 경우"의 예측값이 같아야 함.**
- 생성 AI로 코드를 작성하는 것은 금지되지 않으나 규칙 준수 책임은 참가자에게 있음. 제출 이후 삭제 요청은 불가하며 모든 제출이 검토 대상.

### 3.1b 재검증 (08-29, 실제 script.py 파일 단위 실행, 새 무작위 표본)
- 전체 파일 2회: 33.1초, 두 실행 차이 0.0.
- 6개 범주(F / LG-R 3-0 / LG-R / 비LG R / 투수 콜드스타트 / 타자 콜드스타트) × 4행 = 24행을 각각 **1행짜리 test.csv**로 실행해 전체 실행값과 비교: 23행 단독 = 전체 (최대 |Δ| 1.52e-8, 대부분 1e-9 수준 — NN 커널 부동소수점), 2행짜리 파일 3개 최대 |Δ| 7.4e-9.
- 1행 중단(TEST_044931, `IntCastingNaNError`): 원인은 추론 로직이 아니라 **CSV 재파싱 아티팩트** — 이 행의 `base_state`가 `123`(만루)이라 1행짜리 CSV를 pandas가 정수 열로 읽고, 문자열 키 매핑(`'123'→7`)이 실패해 정수 변환에서 중단. 실제 평가 파일처럼 문자열 값(`___` 등)이 섞인 파일에서는 항상 object 열로 읽혀 발생하지 않으며, 같은 행에 다른 행 1개를 붙인 파일에서는 정상(0.548400901 vs 전체 0.548400899, Δ 2.8e-9). 만루 행은 전체의 3.32%. 단독 실행으로 검증할 때는 `dtype={'base_state': str}`로 읽거나 문자열 값이 있는 행을 함께 넣으면 된다(값에는 영향 없음). 소명 항목에 추가.

- **모든 피처·NN 입력·오프셋·트리 멤버 예측이 배치 구성과 무관하게 비트 단위로 동일**하다. 유일한 비영 차이는 NN 멤버의 1e-8 수준으로, torch가 배치 크기에 따라 다른 float32 행렬곱 커널을 쓰는 데서 오는 부동소수점 차이다(같은 행이 다른 배치 크기에서 계산될 때만 발생; BatchNorm은 eval 모드로 러닝 통계만 사용). 최종 예측 차이 ≤ 9e-9로, 제출 소수점(0.001 단위 정확도)에서 완전히 동일하다.
- 같은 투수·타자·팀·경기·월의 다른 test 행을 넣거나 빼도(E1~E4) 값이 변하지 않으므로, 선수/팀/경기/월 단위 test 집계·순서·과거행 참조는 존재하지 않는다.

### 3.3 발견된 결함: "미학습 투타 조합 단독 실행" 시 중단
- 코드: `add_matchup_features`(L376–393). 입력 프레임의 (투수, 타자) 조합이 학습 통계 `pbs`에 **하나도 없으면** L382–383의 분기가 `pb_prior_shr30` 열을 만들지 않고 `pb_prior_dev`를 NaN으로 두고 반환 → 이후 `F[meta['feats']]`(L940)에서 `KeyError: ['pb_prior_shr30'] not in index`로 **중단**.
- 실증(실제 script.py 실행): 학습에서 만난 적 없는 투타 조합을 가진 가상의 행 1개만 넣으면 KeyError로 중단; 같은 행에 일반 행 1개를 함께 넣으면 정상 예측(0.414774), 3개를 넣어도 동일(0.414774). 즉 예측값 자체는 다른 행에 의존하지 않지만, **그런 행 "1개만" 넣는 실행이 성립하지 않는다.**
- 규모: 새 시즌 행 중 이전 시즌에 없던 투타 조합의 비율은 2023년 45.9%, 2024년 48.8%(학습 데이터 기준 추정) → 실제 2025 평가 행의 약 절반이 단독 실행 시 이 분기에 걸린다. 전체 파일 실행에서는 최소 한 조합이 존재하므로 절대 발생하지 않는다(리더보드 채점 및 8/29 재현 실행 모두 정상).
- 정확한 성격: `keys = np.unique(d.pb_key.values)`(L380)는 **배치에 든 모든 행의 키 집합을 읽는 배치 연산**이며, 그 결과가 정상 경로/조기 반환 경로를 결정한다. 이 연산은 학습 표 `pbs`를 필요한 키로 축소하는 최적화로서 행 A의 값은 A의 키로만 조회되므로 값에는 영향이 없다(행별 조회와 결과 동일; §3.2 실증). 즉 "다른 행의 값이 예측에 반영"되는 일은 없지만, "다른 행의 존재 여부가 코드 경로(출력 유무)에 영향"을 주는 결함이 있다 — 소명에서 이 구분을 그대로 밝힌다.
- **행별 조회 동치 증명**: 배치 키 집합을 전혀 보지 않고 각 행의 (투수, 타자, 시즌)만으로 학습 표를 조회하는 독립 구현을 만들어 제출 구현과 비교했다. (i) 모의 평가 파일 253,507행 전체: `pb_prior_n / pb_prior_rate / pb_prior_shr30 / pb_prior_dev` 최대 차이 0.0. (ii) 행의 50.1%(126,931행)를 학습에 없는 투타 조합으로 바꾼 가상 파일: 전체 행 및 미학습 조합 행만 따로 봐도 4개 피처 최대 차이 0.0(미학습 행의 dev는 0 ± 1e-16). 즉 배치 키 집합은 값에 아무 정보도 보태지 않는 순수 필터이며, 행 A의 값은 행별 조회와 동일하다.
- 판정: 정보 누설은 없으며(다른 행이 값을 바꾸지 않음), 규칙 4항 위반이 아니다. 그러나 재안내 3)의 판정 예시("해당 행 1개만 있는 경우")를 운영진이 문자 그대로 실행해 검증할 경우 약 절반의 행에서 오류로 중단되어 소명이 필요해진다 → **HIGH RISK(검증 강건성)**. 이미 채점된 제출물이라 코드를 바꿀 수 없으므로, 2차 평가 시 이 사실과 원인(L382–383), 수정 1줄(`F['pb_prior_shr30'] = F['p_prior_s_rate'].fillna(0.52)`, `pb_prior_dev = 0.0`)을 명시한 소명서를 함께 제출한다.

## 11. 최종 판정

**[CRITICAL] 명확한 규칙 위반 — 없음.**
전 피처·오프셋·모델·후처리 경로에 test의 다른 행/전체 분포/순서/집계를 쓰는 곳이 없고(코드 추적 + 실행 검증), 외부 데이터·API·사전학습 모델이 없으며, 금지 정보(현재 투구 결과·위치·구종·Trackman, 2025 Trackman)를 입력에 쓰지 않는다.

**[HIGH RISK]**
1. **미학습 투타 조합 행의 단독 실행 중단** (script.py L382–383 → L940 KeyError). 데이터 흐름: 배치에 학습 매치업 키가 하나도 없을 때만 분기. 다른 행이 예측값을 바꾸지 않음(같은 행 + 일반 행 1개/3개/전체 → 0.414774 동일). 관련 원문: 재안내 3)의 판정 예시. 근거: 정보 누설이 아니라 코드 강건성 결함이지만, 운영진이 예시를 문자 그대로 단독 실행으로 검증하면 약 절반의 행에서 오류가 나므로 소명이 필요하다. 조치: 소명서에 원인·1줄 수정·전체 실행 불변성 증빙 포함.

2. **단독 1행 CSV의 `base_state` 정수 파싱** — 만루(`123`) 행만 있는 파일을 pandas가 정수 열로 읽어 코드 매핑이 실패(§3.1b). 추론 로직·값과 무관한 파싱 아티팩트이며 실제 평가 파일에서는 발생하지 않지만, 문자 그대로의 1행 검증에서 3.3%의 행이 중단될 수 있어 소명에 포함(대응: 문자열 dtype 지정).

**[AMBIGUOUS]**
1. **`lg_shift +0.015`의 크기 결정** — 학습 관찰로 범위를 정한 뒤 상수만 다른 제출 3회의 LB 점수로 채택. FAQ 08-12 #12·08-19 #25는 허용, 08-19 #24·08-25 #34는 정도에 따라 프로빙 검토 가능. 운영진 해석 사항. 소명 자료 `docs/CONSTANTS_RATIONALE.md`.
2. **`prob_shift −0.004`** — 학습 근거 있음 + 초기 LB 비교 2회. 위와 같은 성격(위험 낮음).

**[SAFE]** (코드 + 실행 + 공식 근거로 확인)
행 독립성(§3), 데이터 lineage 전 계열(§4), Trackman(§5), 학습/추론 분리(§6), `lg30_shift`·블렌드·클리핑(§7), 외부 데이터/API/모델(§8), 실행 환경·재현성(§9).

### 종합 판정: **C. OPERATOR CONFIRMATION REQUIRED** (조건부)
- 근거: 핵심 lineage와 test-row independence는 실행으로 증명했고 CRITICAL은 없다. 그러나 `lg_shift` 결정 방식은 공식 문서만으로 "명시적으로 허용됨"이라고 단정할 수 없고(#24의 "정도" 판단), 단독 실행 결함은 검증 시 소명이 필요하다. 이 두 가지는 참가자가 해소할 수 없고 운영진의 확인/판단 사항이다.
- 실무적 의미: v48은 이미 제출·채점된 최고점 제출물로 삭제·제외가 불가능하며(재안내 5), 최종 순위 산정 기준이다. 따라서 "제출 여부"가 아니라 **소명 준비와 운영진 확인**이 남은 조치다.
